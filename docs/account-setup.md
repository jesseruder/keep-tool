# Shared account setup

## Claude

`keep accounts setup <target> --share-from <source>` prepares a separate Claude profile for the same work environment. The target keeps its own Claude login and account state while sharing the source profile's instructions and workspace memory.

The setup links `CLAUDE.md`, `skills`, `rules`, `commands`, `agents`, `settings.json`, and `settings.local.json` when they exist. Settings are linked only when they contain no account credential, API-key helper, or provider-routing environment values. The helper refuses a nonempty unmanaged target and never overwrites a conflict.

The helper does not copy or link `.credentials.json`, `auth.json`, a root `.claude.json`, the whole `projects` directory, plugin caches, or marketplace credential state. Log in to the target profile separately. Enabled plugin declarations and marketplace definitions come from shared settings.

Plugins are installed per profile, so setup installs them rather than linking them. After sharing, `keep accounts setup` runs `claude plugin install <id>` in the target profile for every user-scope plugin in the source profile's `plugins/installed_plugins.json` that the target lacks. It runs with the target's config directory and without provider credentials in the environment. Rerunning setup on an existing target installs only what is still missing, and never removes a plugin the target added itself. Setup never adds a marketplace, because `claude plugin marketplace add` writes to `settings.json`, which is the source's file behind a shared link. A plugin from a marketplace that the shared settings do not declare fails with the CLI's error, and setup exits nonzero. `keep doctor` reports a managed Claude account that is missing source plugins as `FAIL: Claude account <id> is missing plugins (...)`, and its fix is the same setup command. A plugin may still need authorization for the target account.

Claude stores memory per project. The launcher calls `ensureSharedMemory(account, cwd)` before a fresh or resumed session. Keep identifies a Git repository through its common Git directory and keeps one source memory directory for that repository. It creates and validates aliases for the exact launch cwd, the current worktree root, and the common/main repository root in both profiles. This covers Claude's project-root lookup for main checkouts, linked worktrees, and nested launch directories without an additional memory setting or launch flag. Every alias must resolve to the same physical directory; Keep refuses an existing divergent directory instead of merging or overwriting it. Outside Git, the canonical working directory is the identity. Claude project directory names replace every non-alphanumeric character with `-`, matching the CLI. Unrelated repositories remain separate.

An explicit `autoMemoryDirectory` in the repository's `.claude/settings.json` or `.claude/settings.local.json` takes precedence. Claude reads that repository setting natively; Keep verifies and prepares its directory instead of adding a command-line override. This avoids changing the invocation class or collapsing every repository into one generated global memory store.

MCP definitions are copied selectively from the source account's `.claude.json`. Keep applies global `mcpServers` first, followed by project definitions for the common/main repository root, the current worktree root, and the exact launch cwd. Repeated canonical paths are applied once, and each later scope overrides conflicts from the earlier scopes. This reproduces Claude's repository-level MCP inheritance inside linked worktrees. No login, trust history, OAuth state, or other `.claude.json` fields are copied. The resulting private `.keep-mcp.json` is passed to Claude with `--mcp-config`. Definitions that rely on external OAuth or keychain state may still require authorization in the target account.

The generated MCP file is managed conservatively. Keep records the SHA-256 of every `.keep-mcp.json` it writes in a sibling `.keep-mcp.json.sha256`. When the source MCP servers change, Keep regenerates the file only if its bytes still match that record; a hand-edited file is refused instead of overwritten. A file written before Keep kept that record is rewritten only if its bytes exactly match the former global-plus-exact-cwd output, or it is Keep's exact, non-empty serialization and every server in it is still defined identically by the source for that cwd. That covers files generated before a server was added; a deletion-only edit to such a file is indistinguishable and is rewritten once, while a file holding a since-removed or changed server remains a conflict. Remove only that generated `.keep-mcp.json` and retry the launch to discard a hand edit. Handoff preflight uses `compatible(source, target, cwd)` and refuses transfer when portable settings or effective MCP tools differ.

Compatibility is direction-independent. A managed profile traces MCP and memory back to its original native profile, so a third profile can be prepared from a second one without losing integrations. Transfers back to the native profile use its native MCP configuration and therefore return no supplemental `mcpConfig`; transfers into a managed profile return its validated `.keep-mcp.json`. Profiles with different effective settings, MCP definitions, or repository memory are refused.

Initial setup is staged in a private sibling directory and renamed into place only after all links and generated files succeed. A failed setup leaves an absent target absent, or restores a pre-existing empty target, so the same command can be retried safely.

## Codex

Adding a nondefault Codex account automatically shares capabilities from the current default Codex account. `keep accounts setup <target> --share-from <source>` performs the same operation explicitly, and the profile launcher refreshes a managed target before every launch.

Keep merges two sets of top-level keys. The capability tables are `features`, `plugins`, `mcp_servers`, `apps`, `marketplaces`, `hooks`, and `experimental_hooks`. The preference keys are `model`, `model_reasoning_effort`, `service_tier`, `project_doc_fallback_filenames`, `shell_environment_policy`, and `projects`. A second profile running a different model, or one that does not read `CLAUDE.md` as a fallback project doc, or one that treats every repository as untrusted, is not the same agent; the merge treats both sets identically.

A scalar or an array key is a single value: `project_doc_fallback_filenames` arrives whole and a reordered list is one decision, not several. A table merges per entry. `projects` therefore yields the union of both profiles’ trust entries, with every entry the target already had preserved; a project path inside the source home is rebased into the target home, and paths outside it are shared unchanged.

Keep links shared `AGENTS.md`, `hooks.json`, local skills, and agent definitions. Exact immutable plugin cache versions are copied through a private staging directory without copying generated plugin runtime state; JSON metadata is rebased for the target home. Local marketplace paths are rebased into the target home; external runtime marketplaces retain their shared external path.

What stays per profile: `notify`, `tui`, `desktop`, `notice`, `auth.json`, `model_provider` routing, history, and plugin app-server or install-staging state. `hooks.state` is inside a shared table, but its trusted-hash keys name the profile’s own `hooks.json` path and are rebased into the target home, so a hash recorded for the source never approves a target hook. MCP server environment and header fields are capability definitions and remain in the private mode-0600 target config. Keep never prints their values in conflict errors or stores them in its manifest; the manifest records hashes.

Sync is a field-level three-way merge. A value Keep previously managed follows source updates. Changing or deleting a managed value in the target makes it an account-local override. Later refreshes preserve that override. If source and target change the same recorded field between refreshes to different values, launch stops and reports only the dotted config path. Resolve the field intentionally, then rerun setup or launch. Existing custom fields at first adoption remain overrides, while equal values become managed.

One exception keeps a transaction from looking like an edit: while a Codex fallback compaction has a pending swap record for the target profile, `model` and `model_reasoning_effort` are frozen for that run. Keep neither writes nor compares them and carries their previous records forward unchanged, so the swapped value is never mistaken for an account-local override and never raises a conflict; the merge resumes on the first refresh after the compaction restores the config and drops its record. `keep doctor` notes this as `(model keys deferred: compaction swap pending)` on an otherwise passing line.

`keep doctor` prints one read-only line per nondefault account: `ok: Codex account <id> shared setup in sync`, `FAIL: ... shared setup behind (<n> values: ...)` when a refresh would change a config value or add or remove a shared link, `FAIL: ... shared setup conflicts (...)` when a field diverged on both sides, and `optional: ... is not sharing setup` when the profile has no manifest. Each failing or optional line carries a `fix:` line with the `keep accounts setup <id> --share-from <source>` that would repair it. Doctor never writes; the Claude side reports drifted shared entries the same way.

Doctor compares config values and shared file links, and nothing else. It does not walk the plugin cache, so a plugin version the source added, changed or removed is not reported: that difference is copied by the refresh at the next launch of that account, or by `keep accounts setup` run explicitly. An account reported as in sync can still pick up plugin work on its next launch.
